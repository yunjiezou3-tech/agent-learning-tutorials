# 从 Hermes 到业务 Agent：一套可运行的售后学习实验

如果你已经接触过 Hermes Agent 的工具循环、`/compress` 和记忆，下一步可以问：**Agent 怎样在多轮对话与进程重启后继续同一项工作，怎样把用户的话变成有边界的业务动作，又怎样证明动作真的做对了？**

这套三章教程用一个电商售后工单回答这些问题。你可以先运行本地演示，再读图与源码，最后替换其中一层做自己的复现实验。它提取 Hermes、DeepSeek Harness、Agent 记忆及评测项目中的设计问题，使用一个足够小的 Python 例子串起来；文中的外部项目链接用于继续深入阅读。

## 三章导航

| 顺序 | 主题 | 从 Hermes 经验接上的问题 | 本地演示 |
| --- | --- | --- | --- |
| [第一章：Agent 如何持续工作](docs/01-continuous-agent.md) | 事件日志、工单状态、短期上下文压缩、长期记忆与恢复 | `/compress` 压缩了什么？会话结束后任务靠什么继续？ | `examples/demo_continuity.py` |
| [第二章：让用户意图落到业务结果](docs/02-intent-to-business.md) | 意图识别、澄清、规则、草稿确认、工具执行与状态核验 | 工具循环何时可以调用有副作用的工具？ | `examples/demo_intent.py` |
| [第三章：让评测反馈到 Agent](docs/03-evaluation-feedback.md) | 固定工单、轨迹与业务状态评分、失败定位、发布门禁 | 改完提示词或流程后，怎样知道旧场景没有变坏？ | `examples/demo_evaluation.py` |

三章共用工单 `T-1001` 和订单 `O-1001`：用户先问能退多少钱，补充订单后申请退款，看到待确认草稿，再明确回复“确认退款”。这条线把**记住工作进度 → 判断下一步 → 核验最终结果**连在一起。长期记忆中的用户偏好可以帮助沟通，但不能代替本次退款确认。

## 直接运行

需要 Python 3.9 或更新版本。默认演示只使用 Python 标准库和本地模拟订单，不需要安装依赖、配置 API key 或连接业务系统。在本仓库根目录依次运行：

```bash
python examples/demo_continuity.py
python examples/demo_intent.py
python examples/demo_evaluation.py
```

验证关键业务边界：

```bash
python -m unittest discover -s tests -v
```

- **持续工作演示**：创建待确认草稿，展示模型可见摘要与完整事件的区别；同一脚本中关闭连接、重建 Agent 实例后，从数据库恢复工单。
- **意图到结果演示**：缺订单号时追问；订单明确后报价并等待确认；确认后提交模拟退款，再查询订单状态。
- **评测演示**：让关键词基线与带业务门禁的候选策略运行同一批售后工单，查看意图、动作、澄清和最终状态的差异及发布判断。

每次运行的业务数据都由脚本在本地建立。`demo_continuity.py` 使用临时 SQLite 文件演示实例重建后的恢复，另外两个演示使用本地模拟状态；不会产生真实退款。

## 项目结构与读代码顺序

```text
docs/                       三章教程、架构图、练习与项目来源
examples/                   每章一个可直接运行的入口
data/eval_cases.json        固定售后工单及预期动作和状态
src/commerce_lab/
  intent.py                 可替换的意图解析器
  agent.py                  工单决策、确认门禁与工具调用
  storage.py                SQLite 事件、订单、记忆和幂等操作
  evaluation.py             离线重放、分层评分与发布门禁
tests/                      关键业务边界的回归检查
```

第一次读代码，建议沿着一轮用户消息走：`intent.py` 提出意图 → `agent.py` 读取工单状态并决定追问、报价或执行 → `storage.py` 记录事件与订单变化 → `evaluation.py` 用同一套业务事实检查结果。这样更容易看清模型可以建议什么，以及哪些决定必须由业务代码校验。

## 一条由浅入深的学习路径

1. **先理解概念**：按三章顺序读产品场景和架构图。把 Hermes 的会话、工具调用和压缩，对照到这里的事件日志、模型可见上下文和业务状态。
2. **再看具体代码**：运行每章演示，把输出中的工单状态、工具动作和订单状态逐一定位到上述四个源码文件。重点追踪“待确认”到“已退款”之间的条件。
3. **最后做一次复现**：先为现有售后助手增加一个新场景和预期业务状态，放进固定工单集重跑；再尝试把同一状态机迁移到预订、采购等场景，重新定义确认、写入和核验规则。

## 教学边界

- 默认使用确定性规则代替大模型，便于观察同一输入为何触发同一动作。`intent.py` 提供可选的兼容接口作为替换入口，但理解和运行三章不依赖外部模型。
- 订单、退款和客户记忆都是本地模拟数据。代码展示确认、幂等和状态复查等机制，不包含真实支付接口、完整售后政策、权限体系或线上部署流程。
- `keyword_baseline` 是故意保留的反例，用来暴露“看到退款关键词就执行”的问题。离线固定工单的结果只说明这组案例上的行为，不代表真实客服效果或企业业务指标。
- 多商品筛选、商品级部分退款执行、复杂争议及工具超时后的人工处理需要继续建模。当前“只退耳机”类诉求会转人工，不会自行退款。章节中的扩展状态机和练习说明了下一步应补哪些约束，不应视为当前代码已覆盖的全部能力。
